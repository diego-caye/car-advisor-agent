# 06 · Memory, sessions, and RAG

## 1. Identity and sessions

- `user_id`: an anonymous UUID generated by the **frontend** on first use (persisted in `localStorage`), sent as the `X-User-Id` header on every request. There's no login: it replaces the baseline's unstable `sessionKey` (gap #2, spec 00).
- `session_id`: created by `POST /api/v1/sessions`, associated with the `user_id` that created it. Every operation on a session (`GET messages`, `GET lead`, `chat/stream`, `chat/confirmations`) validates `session.user_id == X-User-Id` → 404 if it doesn't match (never 403, so as not to confirm another user's session exists).
- Conversation memory: ADK's `DatabaseSessionService` over PostgreSQL (`postgresql+asyncpg://`). Alembic and `scripts/ingest_kb.py` use a separate synchronous DSN (gotcha #2 of section 19 of the master prompt) — same host/DB, different driver.
- Dialog stage and flags (`just_browsing`, `previous_stage`) live in ADK's session state, not in a new table.
- Lead data: persisted **per user** in the `leads` table (PK `user_id`), not per session. **F2 decision:** the table is the single source of truth and the instruction provider queries it on every turn; the lead is **not** duplicated in ADK's `user:`-prefixed state, to avoid two copies that could drift apart. The `user:` prefix exists and is verified (`specs/notes/adk-api.md` §4) and remains available if some future flag needs user-level scope. This way, whoever opens a new session gets greeted by name without repeating the discovery step (AT-02).
- **Conversation title:** its own `session_titles` table (PK `session_id`), not ADK session state. It was first tried with `append_event` + `state_delta`, and a real production issue turned up: the title is generated in the background (`TitleService`, spec 08), and its write competed for the same optimistic lock ADK uses for the active chat turn — if the title was saved while a following turn in the same session was still in flight (typically a message sent quickly after the first one, or a retry), the turn's own `append_event` got rejected with `StaleSessionError`, taking down a real response over a sidebar decoration. An independent SQL table shares no such lock with anything: `SqlSessionTitleRepository` (upsert/get/get_many/delete), never touching the ADK session.

## 2. Controlling history size

- ADK's `EventsCompactionConfig`: a token threshold + N recent events left intact (exact values via env: `MEMORY_COMPACTION_TOKEN_THRESHOLD`, `MEMORY_COMPACTION_KEEP_RECENT`).
- **Forbidden** to trim `contents` by hand in custom callbacks: it can break the thought signatures (`thought_signature`) that Gemini 3 requires in function calling, causing 400 errors on the next turn with tools.
- Since compaction can summarize old messages, the user's language and name **don't depend on the summary preserving them**: they're injected into the instruction from the session/lead state on every turn (spec 05 §1).
- **An explicit summarizer, not ADK's default.** `EventsCompactionConfig.summarizer` is optional; if omitted, ADK defaults to `agent.canonical_model` — the agent's own large model — to write the summary, in the same synchronous call that closes the turn (verified by reading `google/adk/apps/compaction.py`). `create_adk_app` (`agent/factory.py`) instead passes it the same lightweight model already used to title conversations (`GUARDRAIL_MODEL`): summarizing isn't a job for the main model, and adding another call to it right when the conversation is already long — the worst possible moment — would be needless.
- **Tuned against real conversations (F7), not in the abstract:**
  - The number that triggers compaction **is not** the sum of tokens shown in the dev panel (`tokens_in` does accumulate every model call in a turn, including tool-calling ones). ADK's trigger looks at the **latest** call's `usage_metadata.prompt_token_count` in the most recent turn — a single number, not a sum. Confirmed by inspecting real sessions: a turn with `tokens_in=8249` (two calls: 3817 + 4432) left the value ADK actually compares at 4432.
  - With the original threshold (12000, inherited from F2 with no real conversation behind it), **compaction never actually triggered** in a 10-turn conversation that captured a lead and asked two technical questions — real growth is about 300-700 tokens per turn with `gemma4:12b`, so 12000 would only be reached deep into a long conversation, if at all.
  - Lowered to **6000**: in the same class of conversation it would trigger around turn 8-10 (a wide margin against `OLLAMA_CONTEXT_LENGTH`'s 32768), without kicking in during the short 2-5 turn exchanges that are the common case for this advisor.
  - Verified live by forcing a trigger with a low threshold (1500, temporary, test-only): compaction ran with no errors and no `StaleSessionError`, and the summary generated by the lightweight model kept what matters (name, primary use, stage, which tool was called, which question was left unanswered) — no loss of context relevant to the anti-loop behavior of specs 03/04.

## 3. Isolation test (mandatory)

Two or more concurrent sessions from different users, launched with `asyncio.gather`, must never cross names, leads, or history between them. It's an integration test (`backend/tests/integration/`) marked as blocking for F2's DoD — it directly reproduces baseline gap #2 (corresponding AT in spec 09).

## 4. RAG

- Engine: pgvector on the same Postgres instance. `embedding vector(768)` column, HNSW index, cosine distance.
- `Embeddings` port (specs 01, 11): Gemini (`gemini-embedding-001` or `gemini-embedding-2`, truncated/projected to 768 dims) or Ollama (`embeddinggemma`, 768 native dims).
- `kb_chunks` table: `id, chunk_id, title, category, source, content, embedding, embedding_model, content_hash, created_at`.
- **Ingestion** (`backend/scripts/ingest_kb.py`, `make ingest-kb` or `docker compose exec backend uv run python scripts/ingest_kb.py` — `scripts/` and `kb/` are mounted into the backend precisely for this, they aren't copied into the image): reads `kb/*.md` (frontmatter `title`, `category`), chunks by heading (~400–700 tokens, short overlap), computes a `content_hash` per chunk — **idempotent**: if the hash hasn't changed, it doesn't reinsert or recompute the embedding.
- **Startup check:** if the `embedding_model` stored in `kb_chunks` differs from the configured one (`EMBEDDINGS_PROVIDER`/model), the app fails at startup with a clear message asking for re-ingestion — they're different vector spaces and aren't comparable by cosine similarity.
- **Retrieval:** `search_knowledge_base` (spec 03) optionally filters by `category`, sorts by cosine score, and applies `RAG_MIN_SCORE` (env) as an acceptance floor → if it isn't reached, `no_results`.
- KB content: dedicated spec in `00-master-build.md` §12 (15–18 generic markdown docs, no brands or prices).

## 5. Relevant environment variables

`EMBEDDINGS_PROVIDER`, `EMBEDDINGS_MODEL`, `RAG_MIN_SCORE`, `MEMORY_COMPACTION_TOKEN_THRESHOLD`, `MEMORY_COMPACTION_KEEP_RECENT` — documented with default values and examples in `.env.example` (F1).
