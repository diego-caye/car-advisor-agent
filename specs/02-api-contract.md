# 02 · API contract

Base path: `/api/v1`. User auth: `X-User-Id` header (an anonymous UUID generated by the frontend, spec 06). Admin auth: `Authorization: Bearer <ADMIN_TOKEN>` header on endpoints marked `(admin)`. CORS restricted to the frontend origin (`FRONTEND_ORIGIN`). HTTP errors: body `{code, message, retryable}`.

## 1. Endpoints

### `POST /api/v1/sessions`
Creates an ADK session for the `user_id` from the header.
- Body: `{}` (optionally `{"label": str}` in the future, not in P0)
- 200: `{"session_id": str}`
- 401 if `X-User-Id` is missing

### `GET /api/v1/sessions`
Lists the header user's sessions, most recent first.
- 200: `[{"titulo": str | null, "session_id", "last_update_time", "stage"}]`
- `titulo` is a 3–6 word summary of the first message, generated in the background by `GUARDRAIL_MODEL` (the lightweight model) and stored in the session state under the `titulo` key. It's `null` until it's been generated: the frontend shows "New conversation." It never blocks or fails the turn; if the model returns nothing usable, it falls back to the user's own message, truncated to 48 characters.

### `DELETE /api/v1/sessions/{id}`
Deletes a conversation belonging to the header user, along with its events.
- 204, no body
- 404 if the session doesn't exist or doesn't belong to the `user_id` (ownership is checked before deleting, so as not to reveal the existence of another user's sessions)
- The lead is **not** deleted: it lives at the user level, not the session level (spec 06 §1)

### `GET /api/v1/sessions/{id}/messages`
History of a session.
- 200: `[{"role": "user"|"agent", "content", "created_at", "decision"?}]`
- 404 if the session doesn't exist or doesn't belong to the `user_id` from the header
- `decision` [NEW] is the persistent echo of an already-resolved HITL confirmation (spec 03 §3), reconstructed from the ADK events (the `request_human_handoff` tool responds with the final result both when confirmed and when declined, though only the former creates a real handoff): `{"kind": "handoff", "ticket", "ya_existia"}` or `{"kind": "declined", "reason"}`, hung off the last message before the tool's response. Previously this only lived in that tab's React state — reloading the conversation (or opening it in another tab) lost the "handed off"/"not now" notice, and the agent's message was left looking like just another message.

### `GET /api/v1/sessions/{id}/lead`
Current lead record for the user who owns the session.
- 200: `{"lead": {...save_lead fields...} | null, "stage": str, "just_browsing": bool}`
- 404 if the session doesn't exist or doesn't belong to the `user_id`

### `POST /api/v1/chat/stream` (SSE)
Sends a message and streams the response.
- Body: `{"session_id": str, "message": str (1–2000), "model_id"?: str}`
- `model_id` is an `id` from the `GET /api/v1/models` catalog; if omitted, the one matching `AGENT_MODEL` is used (not "the first one in the catalog": with dynamic Ollama discovery, order isn't a design decision, spec 11 §3.1). The model is chosen **per turn**, not per session: it's the same conversation and history is kept across a model change, because the session lives in `DatabaseSessionService`, not in the model. 400 `unknown_model` if the `id` doesn't exist
- 404 if the session doesn't belong to the `user_id` from the header
- Response: `text/event-stream`, events defined in §2
- If a fault injection is active (`X-Debug-Fault`, only under `APP_ENV=dev` and `ENABLE_FAULT_INJECTION=true`), it forces the corresponding error path (spec 07)

### `POST /api/v1/chat/confirmations` (SSE)
Answers a pending HITL confirmation and resumes the turn's stream.
- Body: `{"session_id": str, "confirmation_id": str, "approved": bool, "comment"?: str, "model_id"?: str}`
- It's best to resume with the same `model_id` that requested the confirmation: changing it mid-way through a paused turn mixes two models into a single response
- Response: `text/event-stream`, continuing the same event sequence as `chat/stream`
- 404 if `confirmation_id` doesn't exist or was already resolved

### `GET /api/v1/models`
The model selector's catalog: non-Ollama entries (typically Gemini) come from `MODEL_CHOICES`; Ollama entries are discovered at startup directly against the server itself (spec 11 §3.1), not declared by hand.
- 200: `[{"id", "label", "provider": "gemini"|"ollama", "model", "available": bool, "is_default": bool, "supports_tools": bool, "supports_thinking": bool}]`
- `available` is false when that option's provider isn't configured (Gemini without `GOOGLE_API_KEY`). The UI shows these as disabled rather than hiding them, so it's visible what exists and why it can't be used
- `supports_tools`/`supports_thinking` reflect the model's real `capabilities` (for Ollama, taken from `/api/show`; for manually declared entries, `true` unless stated otherwise) — the UI shows them as icons in the selector
- With no `MODEL_CHOICES` and no Ollama models installed, the catalog has a single entry, the one for `AGENT_MODEL`, and the selector is hidden
- Doesn't require `X-User-Id`: it's deployment configuration, not user data

### `POST /api/v1/feedback`
- Body: `{"session_id": str, "trace_id": str, "score": 1 | -1, "message": str (1-4000), "comment"?: str (≤500)}`
- `message` is the text of the agent response being rated (denormalized at the moment of feedback, not a join against the ADK history — the feedback panel lists it without depending on the session still having that event).
- 200: `{"ok": true}`
- 404 if the session doesn't belong to the `user_id`

### `GET /api/v1/feedback?limit=` [NEW]
- Query `limit?: int` (default 100)
- 200: `[{"id", "session_id", "trace_id", "score", "message", "comment", "created_at"}]`, most recent first
- Crosses other users' sessions (it's a review panel, not a view of one's own data) but **without a token or `X-User-Id`**: the project has no real auth model anywhere else (`X-User-Id` is a UUID the client itself sets), so gating it wouldn't add real security — only friction for whoever is evaluating the challenge. Unlike `/handoffs`, which does change real state (`PATCH`) and stays behind `admin_token`.
- Consumed by the frontend's dev panel ("Feedback" section): it loads on its own when the panel opens, each row is clickable and navigates to `/c/:session_id` for that conversation (fails gracefully — falls back to the draft — if that session isn't the current user's, same check as any other navigation to a conversation)

### `DELETE /api/v1/feedback/{id}` [NEW]
- 204 if deleted; 404 if it doesn't exist
- Same auth criteria as the `GET` above (no `X-User-Id` or `admin_token`): deletes a row from the review panel, not a user's own resource
- Consumed by the dev panel ("Feedback" section): a trash icon per row, same as "Delete conversation" in the sidebar — removes the row locally without reloading the rest of the panel

### `GET /api/v1/handoffs?status=` (admin)
- Query `status?: OPEN | IN_PROGRESS | CLOSED`
- 200: `[{"id", "session_id", "user_id", "reason", "requirement_summary", "preferred_channel", "urgency", "status", "created_at"}]`

### `PATCH /api/v1/handoffs/{id}` (admin)
- Body: `{"status": "IN_PROGRESS" | "CLOSED"}`
- 200: the updated handoff
- 404 if it doesn't exist; 409 if the state transition isn't valid (spec 03 §2)

### `GET /healthz`
- 200: `{"status": "ok"}` with no external dependencies (liveness)

### `GET /readyz`
- 200: `{"status": "ok", "db": "ok", "llm": "ok"}` — checks the Postgres connection and that the configured LLM provider responds to a cheap ping
- 503 if any dependency fails, with detail in the body

## 2. SSE events (`chat/stream` and `chat/confirmations`)

Format `event: <name>\ndata: <json>\n\n`.

| Event | Payload | When |
|---|---|---|
| `message.delta` | `{"delta": str}` | The agent's text. **Emitted exactly once per turn, with the complete response** (see §4) |
| `message.completed` | `{"message_id", "trace_id", "latency_ms", "tokens_in", "tokens_out", "model"}` | End of the turn (success) |
| `tool.started` | `{"name": str}` | Before running a tool |
| `tool.finished` | `{"name", "status", "duration_ms"}` | After running a tool |
| `lead.updated` | `{"lead": {...}, "stage": str}` | After `save_lead` or a stage change |
| `hitl.confirmation_required` | `{"confirmation_id", "reason", "resumen", "preferred_channel", "urgency"}` | The agent proposes `request_human_handoff` and waits for confirmation |
| `handoff.created` | `{"handoff_id", "ticket", "reason", "status", "ya_existia"}` | The handoff was confirmed and is now open. `ya_existia: true` when idempotency returned an already-open one (spec 03 §3) |
| `guardrail.triggered` | `{"layer": "L1"\|"L2"\|"L4", "category": str}` | A guardrail blocked or modified the response |
| `error` | `{"code", "message", "retryable": bool}` | Tool, model, RAG, or DB failure (spec 07) |

A normal turn: `tool.started/finished`* → `message.delta`* → `lead.updated`? → `message.completed`. A turn with a pending HITL confirmation emits `hitl.confirmation_required` and closes the stream; it resumes with `POST /chat/confirmations`, which emits the same sequence (plus `handoff.created` if approved).

## 4. Why text isn't streamed token by token (decided in F6)

The original design sent one `message.delta` per model fragment. When L4 (output filter, spec 07) was implemented, this turned out to be incompatible: **once a delta has been sent, there's no way to retract it from the client**, so a price or a canary leak would already have reached the user by the time L4 detects it on the complete response.

Decision: the backend accumulates the model's text and emits **a single `message.delta`** with the already-reviewed response. We lose token-by-token typing; we gain the guarantee that nothing unfiltered ever reaches the browser.

The feeling of real-time activity is kept by what does stream live: `tool.started` and `tool.finished` (activity chips), `lead.updated`, `hitl.confirmation_required`, and `guardrail.triggered`. The event contract doesn't change, so a client that handles multiple deltas still works.

Discarded alternative: stream raw and emit a replacement event when a leak is detected. Discarded because the unsafe text still reaches the screen, even if only for an instant, and with the canary that's already the leak we were trying to prevent.

## 3. Common HTTP errors

| Code | HTTP | When |
|---|---|---|
| `UNAUTHORIZED` | 401 | Missing `X-User-Id` or invalid `ADMIN_TOKEN` |
| `NOT_FOUND` | 404 | Resource doesn't exist or doesn't belong to the user |
| `VALIDATION_ERROR` | 422 | Invalid body (FastAPI/Pydantic) |
| `CONFLICT` | 409 | Invalid state transition (handoff) |
| `UPSTREAM_UNAVAILABLE` | 503 | DB or LLM down (`retryable: true`) |
